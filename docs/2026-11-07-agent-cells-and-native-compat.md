# Агентские ячейки и нативная совместимость

Дата: 2026-11-07
Дополнение к `docs/2026-11-07-opencode-proxy-design.md`.
Задачи плана: правки к Task 5, 6, 7; новая Task 12.

## Зачем

Параллельные субагенты «висят без вывода». Факты:

- В `proxy.log` 429 `prefill_cap_refused` приходят ровно в моменты запуска агентов
  (13:22:25, 14:06:18) и повторяются каждые ~30 с — это собственные ретраи клиента,
  который всё это время молчит в интерфейсе.
- Все запросы одной сессии, включая субагентов, уходят с одним
  `X-Claude-Code-Session-Id`; различает их только `X-Claude-Code-Agent-Id`.
- Прокси ставит `x-opencode-session` из session id, то есть все агенты претендуют
  на одну ячейку OpenCode и отказывают друг другу по prefill.
- Запущенный бинарник собран до переписывания: ретраев в нём нет, Task 5 не в строю.

Отдельно прокси нарушает контракт Anthropic-шлюза
(https://code.claude.com/docs/en/llm-gateway-protocol.md): не форвардит
`anthropic-beta`, из-за чего молча не работают extended context, interleaved
thinking, tool search, structured outputs и context management.

## Цели

1. Убрать 429, которые прокси создаёт сам себе, при 5 параллельных агентах.
2. Главный ответ всегда получает ячейку раньше фоновых агентов.
3. Не терять prompt cache: префикс промпта не переписывается, ключ ячейки стабилен.
4. Привести запросы/ответы к контракту Anthropic-шлюза (P0-список ниже).

## Non-goals

- Изменение thinking-блоков (сырой CoT остаётся под плашкой — решено 2026-11-07).
- Сессии, PTY, MCP, worktrees, permissions OpenCode — клиенту некуда их показать.
- Эмуляция context management / structured outputs / tool search — отдельная фаза.
- Молчаливая подмена модели главного потока.

## 1. Ключ ячейки

Ключ вычисляется на каждый запрос и уходит в `x-opencode-session`.

| Запрос | Условие | Ключ |
|---|---|---|
| главный поток | нет `X-Claude-Code-Agent-Id` | `s:<session>` |
| субагент | есть `X-Claude-Code-Agent-Id` | `s:<session>:a:<agent-id>` |
| служебный | `X-Claude-Code-Request-Class: auxiliary` | `s:<session>:aux` |
| компакция | `X-Claude-Code-Compaction` присутствует | `s:<session>` (нужен весь контекст) |

`session` — `X-Claude-Code-Session-Id`, при отсутствии — `session_fallback`.
Ключ детерминирован и живёт столько же, сколько цепочка агента: кэш префикса
остаётся на месте на всех ходах этой цепочки.

Ожидаемый эффект: 6 цепочек (главный + 5 агентов) получают 6 ячеек вместо одной.
Общий для всех остаётся только system+tools-префикс, он префиллится один раз на ячейку.

## 2. Очередь и потолок

- На каждый ключ — FIFO-очередь, **один запрос в полёте**. Внутри цепочки запросы
  и так последовательные, очередь нужна только чтобы не устроить prefill-конфликт.
- Приоритет между ключами: `main` > `subagent` > `auxiliary`. Главный ответ не
  стоит за пачкой фоновых агентов.
- Глобальный семафор `max_concurrent_cells` (по умолчанию 8) ограничивает число
  одновременных ячеек; лишние ждут в очереди с приоритетом.
- Таймаут ожидания в очереди `queue_timeout_ms` (по умолчанию 60000); по истечении —
  Anthropic-ошибка `overloaded_error` с `retry-after`.

## 3. Ретрай с keepalive

Проблема: пока прокси ждёт и повторяет, клиент не получает ни байта и считает, что
поток повис. Для стриминговых запросов (`stream: true`):

1. Дождаться первого ответа upstream до `keepalive_after_ms` (по умолчанию 3000).
2. Если ответа нет или upstream ответил 429 — сразу отдать клиенту
   `200 OK`, `Content-Type: text/event-stream`, и слать `event: ping`
   каждые `keepalive_interval_ms` (по умолчанию 5000).
3. Продолжать ретраи наверх; при первом успешном ответе — транслировать его SSE
   клиенту как обычно.
4. Если все попытки исчерпаны — отдать `event: error` с телом Anthropic
   (`{"type":"error","error":{"type":"overloaded_error","message":"..."}}`).

Для нестриминговых запросов ничего не меняется: ждём и ретраим, отдаём статус как есть.

Риск: после `200` статус клиенту уже не поменять. Поэтому ошибка уходит только
событием `error`, а тест должен проверять, что клиент её распознаёт.

## 4. Кэш

- `system`, `messages`, `tools` не переписываются. Никаких вставок в начало.
- `cache_control` пробрасывается как есть, включая `ttl`.
- Ключ ячейки не меняется в течение жизни цепочки.
- Ротация ключа (см. §5) — единственное исключение, и она сознательно теряет кэш.

## 5. Фолбэк

Если ячейка отказывает дольше `fallback_after_ms` (по умолчанию 20000):

- для `subagent` и `auxiliary` — провернуть ключ (`...:r2`, `:r3`) и получить новую
  ячейку; кэш этой цепочки теряется, но работа продолжается;
- для `main` — только если `fallback_rotate_main: true`; по умолчанию выключено,
  чтобы не менять поведение главного ответа без явного согласия.

## 6. Конфиг

```json
{
  "scheduler": {
    "max_concurrent_cells": 8,
    "queue_timeout_ms": 60000,
    "keepalive_after_ms": 3000,
    "keepalive_interval_ms": 5000,
    "fallback_after_ms": 20000,
    "fallback_rotate_main": false
  }
}
```

Пустые/нулевые значения заменяются дефолтами (как в остальном конфиге).
Секция читается по mtime, как весь конфиг.

## 7. Нативная совместимость (P0)

Входит в Task 5/7:

1. Пробрасывать `anthropic-beta` и все `anthropic-*` заголовки verbatim, без allowlist.
2. Не заворачивать ошибки upstream в собственный конверт: тело ошибки уходит клиенту
   байт в байт. Если обёртка неизбежна — сообщение обязано содержать
   `capability_rejected: beta_header:<value>`, иначе клиент не сможет отключить фичу.
3. Переписывать `model` в ответе: JSON-ответ и `message_start` в SSE → запрошенный id.
4. `GET /v1/models`: `{"data":[{"type":"model","id":"claude-…","display_name":"…"}]}`,
   только id, содержащие `claude`/`anthropic`, ответ ≤3 с, без редиректов.
5. `count_tokens` — пробрасывать, кэшировать одинаковые тела на 60 с.
6. `HEAD /api/hello` — отвечать 200 локально.
7. Во время ретраев — `event: ping` (см. §3).

## 8. Наблюдаемость

В строку лога добавить: `cell=<key>`, `queue_ms=`, `agent=<id>`, `class=<request_class>`.
В `Stats` добавить: `Queued`, `QueueWaitMS`, `CellsInUse`, `Keepalives`.
`/admin/status` отдаёт их вместе с текущим числом ячеек и очередей по ключам.

## 9. Открытые допущения (проверяются на живой работе)

- Ячейка OpenCode выбирается по `x-opencode-session`. Проверка: частота 429 до/после
  на одинаковой нагрузке (5 агентов + главный).
- У аккаунта есть предел одновременных ячеек. Если при разных ключах 429 не исчезают —
  уменьшить `max_concurrent_cells` до фактического предела; схема вырождается в очередь,
  но приоритет главного сохраняется.

## 10. Критерии приёмки

- 5 параллельных субагентов + главный: нет 429, вызванных конкуренцией за одну ячейку.
- Главный ответ не ждёт фоновых агентов дольше одного хода агента.
- Префикс промпта не меняется между ходами: cache read остаётся ненулевым.
- `anthropic-beta` виден upstream (проверка захватом заголовков).
- Тело ошибки upstream доходит до клиента без изменений.
- `/v1/models` отвечает <3 с и не редиректит.
- Тест на keepalive: при искусственном 429 upstream клиент получает `ping`, затем
  либо поток, либо `event: error`.

## 11. Конфиг приложения (Task 8/9, генератор)

Генератор `models.json` → профиль приложения должен дополнительно выпускать:

```json
"inferenceModelPricingEnabled": true,
"inferenceModelPricing": [
  { "name": "claude-DeepSeek-v4.1-Flash",
    "inputPerMtok": 0.15, "outputPerMtok": 0.6,
    "cacheReadPerMtok": 0.003, "cacheWritePerMtok": 0.1875 }
]
```

- Ставки берутся из `models.json[].pricing` (input/output/cache_read), `cache_write`
  по умолчанию = input × 1.25, если каталог не даёт другого.
- `inferenceModelPricingMultiplier` не ставить (или 1): схема разрешает 0 < m ≤ 1.
- Ключ `name` — ровно тот id, который уходит в запросах (пикер), иначе override не сработает.
- `behavesAs` выбирается так, чтобы контекст в Claude Code совпадал с реальным: для модели
  с 1M это должен быть 1M-способный id, плюс `supports1m: true`. Иначе клиент считает 200K.
- Если приложение не выводит контекст из `behavesAs`, задать `modelOverrides` в settings:
  запись на alias с реальным `contextWindow` и возможностями (thinking/effort/tools).

**Перезапуск обязателен.** `configLibrary/*.json` читается главным процессом приложения
при старте и при смене профиля; правка файла на ходу не подхватывается. После генерации
профиля — либо полный Quit и запуск, либо переключение профиля туда-обратно. Навык
`claude-config` должен об этом предупреждать.

## 12. Следующая фаза (сознательно не сейчас)

- `anthropic-ratelimit-unified-*` из накопленного `allowance` и плана — чтобы CLI сам
  показывал остаток лимита; на 429 отличать план от временного троттлинга.
- `x-claude-code-context-compacted` — дропать кэш ключа после компакции.
- `x-should-retry` — прокидывать решение upstream вместо собственной эвристики.
- Атрибуционный блок в начале system: уходит в промпт сторонней модели; либо
  пробрасывать `system` как есть (уже требование §4), либо `CLAUDE_CODE_ATTRIBUTION_HEADER=0`.
- Эмуляция web search / context management / structured outputs — отдельный дизайн.

**Про OpenCode API.** API локального сервера живой: десктопное приложение держит
`opencode-cli serve --service` на `127.0.0.1:<port>` (сейчас 49374). Прямой `curl`
получает `401 UnauthorizedError` — токен сервера наружу не выдаётся. Но CLI умеет
ходить в свой сервер сам: `opencode api GET /api/info` работает без токена, это готовый
мост для прокси (шелл-аут вместо работы с секретом).

Что показал локальный API на этой машине (2026-11-07):

- `/api/experimental/usage/limits` → `{"data": null}`: локальный сервер не привязан к
  Go-подписке, лимитов не знает. Реальные лимиты по-прежнему считаем из `allowance`.
- `/api/model` → 23 модели, все бесплатные (`*-free`, `glm-5.3-free`, …), платных
  `deepseek-v4.1-flash` и прочих Go-моделей нет; `cost` у всех нулевой.
- `/api/provider` → публичный `https://opencode.ai/inference/openai/v1`, MLX-локальный
  и Z.AI. Go-провайдера нет.
- `/api/websearch/provider` → exa, firecrawl, parallel, tavily, tinyfish (список
  поддерживаемых; ключи надо настраивать отдельно).

Вывод: для нашей задачи локальный API почти ничего не даёт. Сессии и форк — его
собственный рантайм, не ключи шлюза. Лимиты и каталог приходят из шлюза. Единственное
полезное — бэкенд веб-поиска, если настроить провайдера, и матрица `Model.Compatibility`
для тех моделей, что через него идут (не Go-каталога).

Токен, который присылался вручную, локальный сервер не принял ни как `Bearer`, ни как
`x-api-key`, ни в query/cookie — это ключ другого сервиса, не локального API.

## 13. Thinking: свёрнутая плашка

Сейчас плашка размышлений всегда развёрнута и не сворачивается. Причина найдена в
рендере приложения: подпись элемента берётся из `summaries[0].summary`, а флаг
`opensInPlace` (развернуть на месте) выставляется только когда у блока есть
`firstRawLine` и `labelOnly` ложно. У блоков opencode `summaries` нет, поэтому подпись
строится из первой строки сырого текста, и блок открывается развёрнутым.

Требование: в SSE `content_block_start` (и в нестриминговом JSON) для каждого
thinking-блока добавлять:

```json
"summaries": [{ "type": "summary_text", "summary": "<короткая строка>" }]
```

- `summary` — первая содержательная строка `thinking`, очищенная от markdown
  (заголовки, списки, бэктики, ссылки), не длиннее 160 символов.
- Поле `thinking` не меняется: при раскрытии виден полный сырой текст.
- **Задержка старта блока** (одобрено пользователем 2026-11-07): `content_block_start`
  thinking-блока держится до первой строки текста, но не дольше `thinking_summary_wait_ms`
  (по умолчанию 500) и не больше 256 байт накопленного текста. Если строка не собралась —
  блок отдаётся с `"summary": "Thinking"`. Остальные события блока (`thinking_delta`,
  `content_block_stop`) идут без изменений, порядок не нарушается. Задержка влияет
  только на момент показа плашки, не на токены и не на содержимое.
- На пути наверх (в истории `messages`) `summaries` вырезать, чтобы не уходили в opencode.
- `signature` не синтезировать: для свёртки он не нужен, а выдуманная подпись
  рискует сломать проверку preserved thinking.
- Проверка на живой работе: плашка «Thought for Ns» свёрнута, по клику показывает
  сырой текст.
